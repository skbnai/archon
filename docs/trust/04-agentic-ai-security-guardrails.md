For agent credential identity (SPIFFE/SPIRE, IETF AIMS, Entra Agent ID), see [Agentic AI Security & Identity](05-agentic-ai-security-identity.md) — that guide covers Layer 1 (identity); this one covers all 18 threat classes with architectural controls, the 14-layer guardrail map, and how tech giants operationalize these defenses at scale. This part covers the core doctrine, the full threat catalog, the threat-model method, and the guardrail architecture; [Part 2](parts/04-agentic-ai-security-guardrails-part2.md) covers vendor implementations (Google, Microsoft, AWS), consultancy frameworks, real-world case studies, compliance overlay, and the security architecture review checklist.

## Core Security Doctrine

The foundational principle, drawn from production deployments at scale: prompt injection is not reliably detectable — it is survivable. Architect so that a fully hijacked agent still cannot cause unacceptable harm: least privilege, egress control, human gates on pivots, and blast-radius isolation. Detection layers reduce frequency; architecture bounds severity. This inverts classical application security's detect-and-block-at-the-perimeter posture — agentic AI security assumes some attacks succeed and designs the system so even a fully compromised agent cannot produce catastrophic outcomes.

Three architectural principles follow: least privilege per agent (each agent gets the minimum tool set required, no cross-agent tool sharing without explicit policy); egress control as an invariant (all agent outbound traffic flows through a proxied allowlist, no direct internet egress from agent runtimes); and blast-radius isolation (tenant/workload separation ensures a compromised agent in one namespace cannot read or affect another). Standards framing: OWASP Top 10 for LLM Applications (LLM01-LLM10) covers model-level risks; OWASP Agentic AI Security extends this to nine agentic-specific threat classes (memory poisoning, tool misuse, privilege compromise, cascading hallucination, intent manipulation, identity spoofing, rogue agents, HITL bypass, inter-agent communication attacks); governance overlays include the NIST AI RMF (Map/Measure/Manage/Govern), ISO 42001 AIMS, and EU AI Act high-risk obligations.

## Threat Catalog: 18 Attack Classes

Each class maps to four treatment stages: Architecture (structural prevention), Detection (signals firing during an attack), Mitigation/Containment (active response), and Recovery (restoring integrity afterward).

**Input and context threats.** Direct prompt injection (a user crafts input overriding policy) is prevented via instruction hierarchy, a system-prompt integrity hash, and input classifiers; detected via injection classifiers, jailbreak heuristics, and refusal-rate anomaly; contained by refusing/stripping and degrading to a restricted toolset; recovered via session quarantine and detector updates from the pattern. Indirect injection (instructions embedded in retrieved docs, webpages, emails, or tool results) is prevented via provenance tagging of untrusted spans, spotlighting/delimiting, and lethal-trifecta separation (private data, untrusted content, and egress never co-resident); detected via tool-result scanners, canary instructions, and egress DLP hits; contained by dropping the tainted span and requiring approval for post-taint actions; recovered by purging tainted context/memory and blocklisting the source. Context poisoning (an adversary shapes long-lived context like files or tickets the agent will read) adds content signing for internal sources on top of indirect-injection controls; detected via diffing trusted sources and write-audit on agent-readable stores; contained by re-fetching from the source of record; recovered by invalidating derived memories by provenance.

**Memory and persistence threats.** Tool poisoning (malicious MCP tool descriptions or rug-pull updates) is prevented via a private registry, manifest hash pinning, and review tiers; detected via manifest-change alerts and behavioral diffing of tool outputs; contained by suspending the server and downgrading its tier; recovered by rotating credentials it saw and auditing calls since the change. Memory poisoning (implanting persistent instructions/facts into long-term memory) is prevented via gated writes, provenance, and a quarantine pipeline; detected via write anomaly detection and an instruction-like-memory classifier; contained by quarantining records; recovered via bulk invalidation by provenance or time window. Vector DB poisoning (adversarial embeddings/documents steering retrieval) is prevented via ingest validation plus provenance, per-tenant collections, and embedding-space outlier checks (OWASP LLM08); detected via retrieval-quality drift and outlier density; contained by removing vectors and re-embedding the clean corpus; recovered via snapshot restore of the collection.

**Identity and credential threats.** Agent impersonation (a rogue process claims agent identity) is prevented via SPIFFE attestation-issued identity with no static agent API keys; detected via cert/token misuse analytics and unknown-SVID alerts; contained by revoking the SVID (stopping renewal); recovered by re-attesting the fleet and auditing actions under the stolen identity. Tool impersonation (a fake MCP server or typosquatted card/package) is prevented via signed Agent Cards (A2A), registry-only resolution, and TLS pinning to registered endpoints; detected via card-signature failures and endpoint drift; contained by blocking and catalog-alerting; recovered by purging results consumed from the impostor. Identity/credential theft (a token exfiltrated from a sandbox or logs) is prevented via short-TTL, DPoP/mTLS-bound, audience-scoped tokens with secrets never in context and log redaction; detected via token-replay detection and impossible-travel analytics for workloads; contained by stopping renewal and killing sessions; recovered by rotating and reviewing the actor-chain audit.

**Output and action threats.** Data exfiltration (a hijacked agent leaks via tool params, URLs, DNS, markdown images, or A2A artifacts) is prevented via an egress allowlist, DLP on all outbound traffic, and no raw-context sharing across boundaries; detected via DLP alerts and unusual destination/volume; contained by blocking the channel and killing the task; recovered via incident response and rotating exposed secrets. Hallucinated actions (an agent invents a tool, parameters, or entities, causing wrong real-world effects) are prevented via schema validation (a nonexistent tool is a hard fail), reference-validity checks, and acceptance criteria; detected via verification-gate failures and downstream reconciliation breaks; contained by blocking the commit and re-planning; recovered via saga compensation of committed steps. Jailbreaks (roleplay, encoding, or multi-turn erosion of safety) are prevented via layered safety engines and conversation-level (not turn-level) analysis; detected via multi-turn drift detectors and shared industry severity rubrics; contained by terminating the session and restricting capabilities; recovered via red-team findings feeding filter retraining.

**Supply chain and infrastructure threats.** Supply chain compromise (of a model, SDK, MCP package, prompt template, or fine-tune data) is prevented via signed artifacts (Sigstore), an SBOM plus AI-BOM (models, datasets, prompts), pinned versions, and private mirrors; detected via dependency scanning and registry diff alerts; contained by version rollback and registry freeze; recovered by rebuilding from attested sources. Sandbox escape (malicious agent-written or tool code breaks isolation) is prevented via microVM/gVisor, syscall filtering, no host mounts, an egress proxy, and non-root execution; detected via runtime sensors (Falco-class) catching unexpected syscalls/egress; contained by killing the microVM (disposable by design); recovered by rebuilding from image with a forensic snapshot. Model extraction/abuse (systematic querying to clone or misuse capacity) is prevented via gateway quotas, anomaly-based throttling, and watermark/canary responses; detected via query-distribution analytics; contained by rate-limiting and banning keys; recovered via legal/contractual action.

**Multi-agent and human-layer threats.** Cross-agent contamination (a compromised agent spreads instructions via shared memory, messages, or A2A) is prevented via mediated edges only, per-agent namespaces, and content screening on inter-agent messages; detected via lineage tracing of which agents consumed a given input; contained by isolating the agent (identity revoke); recovered via a contamination graph walk invalidating downstream state. Insider threat (a privileged human abuses the agent platform — policy edits, registry, memory) is prevented via separation of duties, two-person review for policy/registry changes, and fully audited admin actions; detected via UEBA on admin operations; contained by freezing the change and reviewing access; recovered by restoring signed policy bundles. HITL bypass/approval fatigue (flooding approvals or crafting misleading summaries) is prevented via an approval UI showing the raw action and diff rather than agent prose, rate limits on approval requests, and risk-tiered routing; detected via approval-latency and override analytics; contained by auto-denying on timeout and batch-suspicious-escalation; recovered via retrospective review of approvals granted under flood.

## Threat-Model Method

Apply STRIDE per trust boundary (as defined in the architecture's trust-boundary diagram) combined with the OWASP Agentic AI taxonomy per component. Maintain a risk register with owner, likelihood×impact score, control mapping (ISO 27001 Annex A plus AI-specific controls), and test evidence (red-team findings, automated injection test results). Continuous adversarial testing runs on a defined cadence: every CI run gets automated injection suites (promptfoo/garak-class tooling) across regression fixtures; weekly gets automated red-team scanning against staging; quarterly gets human red-team exercises and bug bounty scope review including agent behaviors; and every model version change triggers a full injection-plus-jailbreak suite re-run before promotion.

## Multi-Layer Guardrail Architecture

Production guardrail stacks combine two fundamentally different control types. Deterministic controls (regex/schema/policy/allowlists/quotas) give the same verdict for the same input every time and are fully auditable — use them for invariants: spend caps, tool allowlists, PII patterns, schema validation, egress domains, approval routing; they should never fail silently, since errors must be actionable. Probabilistic controls (classifiers, guard models, critic LLMs, Bedrock Guardrails, Azure Content Safety, Model Armor, Llama-Guard-class) handle semantics deterministic rules cannot, but carry error rates — never the sole control for an unacceptable outcome — and their FP/FN rates must be tracked as SLOs, since a guardrail with unmeasured error rate is decoration. The composition rule: deterministic outer shell, probabilistic inner filters — probabilistic verdicts can tighten (escalate/deny) but never loosen a deterministic deny.

Every guardrail in production must emit telemetry (fired/passed/latency metrics on every evaluation), be individually toggleable (a feature flag per layer, not a monolithic on/off), be tested in CI (adversarial fixtures testing each guardrail independently), and ship through release governance (the same pipeline as code — PR review, eval gate, staged rollout).

## The 14-Layer Guardrail Map

Twelve layers pair deterministic with probabilistic controls: Input (length/format limits, encoding normalization, known-pattern blocklists, system-prompt hash check paired with injection/jailbreak classifiers and intent screening); Output (schema validation, secret/PII regex+detectors, link/domain allowlist, license/copyright rules paired with toxicity/harm classifiers and groundedness/hallucination scoring against sources); Context (budget enforcement, required provenance tags, untrusted-span delimiting paired with contextual-relevance and contradiction detection); Memory (write ACLs, provenance-gated persistence, TTL paired with instruction-like-memory and poisoning classifiers); Planning (plan-schema validation, pivot-step approval routing, depth/budget caps paired with plan-risk scoring and a feasibility critic); Tool (schema+type validation, idempotency keys, per-agent allowlists, parameter bounds, rate caps paired with argument-anomaly detection and result-injection scanning); Policy (a Cedar/OPA PDP on every action, fail-closed, paired with a risk engine adjusting approval thresholds); Infrastructure (sandbox profiles, egress proxy, mTLS, quotas paired with runtime behavioral anomaly detection); Model (pinned provider safety configs, a model allowlist per data class paired with inherited constitutional/RLHF alignment and guard-model ensembles); Human (mandatory approval gates on risk tiers, step-up auth, timeout-equals-deny paired with sampling-based human QA of "green" outputs); Governance (release gates requiring eval thresholds to pass, registry enforcement paired with continuous eval drift monitoring); and Compliance (residency routing, retention/legal hold, audit completeness checks paired with automated compliance-evidence classification).

Map each threat from the catalog above to the layers that address it — gaps where no layer covers a threat class are architecture risks. The most common gap pattern: memory and context layers are often the weakest in early deployments, since teams build input/output guardrails first and neglect the persistence plane.
