This guide covers the connective tissue of an agent platform: how agents communicate (channel catalog, delivery semantics, sagas), how every action attributes to a cryptographically verifiable identity chain, how authorization composes (RBAC → ABAC → ReBAC → capability tokens → risk overlay), and the AI gateway as the single mediated path for all inference traffic. For the credential/identity standards stack (SPIFFE/SPIRE deployment, OWASP ASI, Entra Agent ID), see [Agentic AI Security & Identity](05-agentic-ai-security-identity.md); for a concrete gateway implementation, see the [Kong AI Gateway guide](../platforms/08-kong-ai-gateway-guide.md).

## Agent Communication

Ten mechanisms serve distinct roles: A2A handles cross-framework/cross-org agent-to-agent tasks via Agent Cards, task lifecycle, and Artifacts (JSON-RPC/gRPC bindings, SSE streaming) — vendor-neutral with discovery, auth, and streaming in one spec, though operational tooling remains young. MCP handles agent-to-tool/data access (tools, resources, prompts; the 2026-07-28 spec adds a stateless HTTP core plus a Tasks extension) — the dominant tool standard (~10K public servers) with OAuth-aligned authZ, though tool descriptions are an injection surface and third-party server trust is on you. HTTP/REST provides the universal synchronous substrate under MCP/A2A but forces you to build retries, idempotency, and streaming semantics yourself. gRPC gives low-latency internal agent-to-service communication with streaming, deadlines, and native mTLS, at the cost of browser/edge friction. WebSocket gives full-duplex realtime UX streaming but its stateful connections fight autoscaling — prefer SSE where one-directional suffices. Kafka/Redis Streams provide a replayable event backbone with per-key ordering, but ordering only holds per key and poison messages need DLQ design. SQS/SNS/EventBridge give zero-ops managed queueing with built-in DLQ and redrive, though standard SQS is at-least-once and unordered (FIFO trades throughput for ordering). Shared memory/vector store/KG enables blackboard-style indirect coordination but risks poisoning and staleness, requiring provenance and ACLs. Shared filesystem/Git workspace lets coding agents coordinate via a diffable, versioned repo with free audit/rollback, at the risk of merge-conflict coordination failures and secrets-in-workspace exposure. CRDTs give conflict-free convergence for shared docs/plans, but "converged" doesn't mean "correct." Generic pub/sub decouples ambient/reactive agents but varies in delivery/ordering guarantees — design for duplicates.

Exactly-once delivery does not exist end-to-end. Production systems achieve effectively-once processing: at-least-once delivery plus idempotent consumers. Idempotency keys on every mutating tool call (`key = hash(task_id, step_id, action_fingerprint)`, Stripe's pattern) neutralize retry storms, duplicate deliveries, and replay after checkpoint resume. Guarantee ordering only where semantics require it (a per-task partition key) — cross-task global ordering is an anti-requirement. Never attempt 2PC across tools; agent workflows are long-lived, so use Sagas: each step registers a compensating action in the tool registry (book→cancel, create→delete, send→recall-or-notify), with the workflow engine (Temporal) executing compensation on failure. Steps without a possible compensation — external emails, payments — are pivot points requiring pre-commit approval gates, placed as late as possible in the plan. Prefer artifact-passing (immutable object-store snapshots) over live shared mutable state; where live sharing is needed, use versioned reads or CRDTs for the narrow types that fit. Promise read-your-writes within a task, eventual consistency across agents, and causal ordering where the event bus preserves per-key order — document this, since agents assuming stronger consistency generate phantom bugs.

Channel choice follows the situation: synchronous capability invocation uses MCP; delegating a task with lifecycle to another agent uses A2A; decoupled reaction to business facts uses events; large artifacts pass by handle via object store or Git references, never inlined into context; anything crossing an org boundary uses A2A over mTLS with signed cards and a contract allowlist.

## Authentication and Identity

Every action must attribute to a chain — human principal → agent identity → sub-agent → tool/MCP server → downstream API — with each link cryptographically verifiable. The central 2025-26 agent security problem is the delegation gap: OAuth was built for "app acts for user," not "ephemeral agent #4711, spawned by agent A, acts for user U within task T."

Identity mechanisms differ by boundary. Human identity anchors via OIDC (enterprise IdP — Entra, Okta, Ping) with phishing-resistant MFA for step-up approval on high-risk actions. Agent (workload) identity uses SPIFFE/SPIRE SVIDs (X.509 or JWT) issued per runtime via node-plus-workload attestation, or cloud-native equivalents (IAM roles, Entra Workload ID, GCP WIF) — agents are born with identity from platform attestation, never baked-in secrets, with minutes-scale SVID TTL and automatic rotation. Sub-agent identity derives a child SVID or STS-minted scoped token carrying task context, with spawn depth and scope monotonically non-increasing — delegation only narrows privilege. Tool/MCP server identity uses OAuth 2.1 per the MCP auth spec, with the MCP server as resource server and tokens audience-bound via mandatory RFC 8707 resource indicators — token passthrough (forwarding the user's upstream token to downstream APIs) is explicitly forbidden by spec. External API identity uses RFC 8693 token exchange at an internal STS: the agent presents its SVID plus user context and receives a short-lived, audience- and scope-narrowed token — the STS is where enterprise delegation policy actually lives. Infrastructure identity uses mTLS everywhere via service mesh with no ambient instance credentials inside agent sandboxes, egressing through an identity-aware proxy.

Token doctrine: everything is short-lived (access tokens ≤15 minutes for agent contexts, minutes-scale SVIDs, platform-handled refresh — rotation is continuous by construction, revocation is just "stop renewing"); tokens crossing a network hop are sender-constrained via DPoP (RFC 9449) or mTLS binding, so a stolen bearer token from a compromised sandbox is useless elsewhere; context/capability tokens embed `task_id`, purpose, human principal, and expiry as claims, with downstream PEPs authorizing on the full tuple — possession of a narrowly-scoped, unforgeable token is the authorization (macaroon/Biscuit-style attenuation where supported); a cryptographic delegation chain has each hop sign a delegation assertion (the `act` claim in RFC 8693 exchange), producing an auditable chain enforced today by the internal STS pending emerging standardized OAuth agent-OBO work; MCP's Dynamic Client Registration against the enterprise AS, hardened in the 2026-07-28 spec (RFC 9207 `iss` validation, AS-bound credentials, declared `application_type`), closes real mix-up attacks and should be adopted now; SPIRE attestors verify what is actually running (image digest, node, k8s SA) before issuing identity — identity without attestation is a name, not a proof; and agents never see long-lived secrets, since tool credentials live in the tool-execution layer or secrets manager, injected per-call server-side.

## Authorization

Model selection by use: RBAC gives baseline entitlements (which roles may deploy/invoke which agents) but is too coarse alone, exploding role counts. ABAC is the workhorse, deciding over principal/action/resource/context attributes (task purpose, risk score, time, data classification, environment). ReBAC (Zanzibar-style via SpiceDB/OpenFGA) answers data-scoped questions like "may this agent read this document," mirroring doc/folder/org graphs — ideal for memory and retrieval ACLs. PBAC/policy-as-code is the delivery mechanism for all the above, via Cedar (AWS Verified Permissions, formally verified, default-deny, forbid-overrides-permit) or OPA/Rego (CNCF, ubiquitous in k8s/gateways). Capability tokens deliver runtime least privilege by minting per-task capability sets so the agent literally cannot name actions outside its granted tool manifest. A risk-and-context-aware overlay scores each action (novelty, blast radius, data sensitivity, anomaly signals) and maps thresholds to allow, allow-with-logging, require-approval, or deny. Recommended composite: RBAC for coarse entitlements, ABAC/Cedar for per-action decisions, ReBAC for data access, capability manifests at runtime, and a risk engine for HITL escalation.

Policy mechanics: adopt Cedar semantics platform-wide even on OPA — default deny, explicit forbid always beats permit, most-specific-scope wins only through explicit policy structure, never implicit precedence (ad-hoc precedence is where audit findings live). Layer policies from platform invariants (non-overridable forbids — no prod-DB writes without approval, no PII egress to unapproved models) through domain policies, team/agent policies, to task-scoped grants, where lower layers may only restrict, never expand — enforced via a policy-bundle build pipeline (policies are code: PR review, tests, CI, signed bundles). Keep dynamic context (risk score, budget remaining, kill-switch flags) injected at decision time from the platform while the policy text itself stays static and versioned — dynamism lives in data, not in mutating rules. Every PDP decision logs the policy bundle hash, request tuple, decision, and obligations, since replayable authorization decisions are a regulator-grade requirement (EU AI Act logging, SOC 2 CC6). Delegation grants are first-class objects (grantor, grantee agent, scope, task, expiry, revocation handle) stored centrally and consulted by the STS at minting time, unifying identity with policy. PEPs sit at the AI gateway (model actions), tool gateway/MCP proxy (tool calls), memory service (reads/writes), A2A edge (inter-agent), and workflow engine (step transitions) — one PDP, many PEPs, with decisions cached for seconds at most and invalidated by events.

## The AI Gateway

Without a gateway, every team wires model credentials into app code — no unified audit, no cost control, no kill switch, no redaction, N incompatible provider SDKs, and scattered compliance evidence. The AI gateway (LiteLLM, Portkey, Kong AI, Cloudflare AI Gateway, Apigee-class, or in-house on Envoy) is the single mediated path for all inference traffic, the model-side twin of the API gateway, sitting between the agent plane and all model providers and increasingly doubling as the MCP/tool gateway on the action side.

Its responsibilities span twelve areas: authentication (terminating workload identity via SVID/OIDC, with virtual keys per team/agent mapped to real provider credentials held only here); authorization (a PEP-to-PDP call per request — may this agent use this model/feature at this size for this data class); prompt inspection (injection classifiers and policy screens before spend); PII redaction (deterministic detectors like Presidio plus format-preserving tokenization on egress to external models, de-tokenized on response where permitted, residency-aware); rate limiting (token-based, not just RPS, per tenant/agent/task, with fair-share under provider throttling); routing (policy-driven task-class-to-model-tier mapping, residency pinning, and capability fallbacks with declared semantic equivalence classes); cost management (real-time per-request metering against a pre-flight budget check, with downgrade-or-halt obligations from policy); caching (exact and semantic caching with cache scope keys per tenant/data-class, never shared across trust domains, honoring provider prompt-caching for KV reuse); audit and provenance (an immutable, access-controlled request/response log trace-ID linked, plus prompt provenance tags on every context segment — origin: user/system/retrieval/tool-result — so injection forensics can reconstruct who said what); tool mediation (validating tool-call JSON against registered schemas, stripping hallucinated tools, and an output safety pass before returning); tenant isolation (per-tenant keys, headers, quotas, caches, no cross-tenant batching); and context validation (enforcing context budget, rejecting over-window requests, verifying a tamper-evident system-prompt hash header). The gateway sits on the hot path of every token, so engineer it like an L7 load balancer: stateless, horizontally scaled, with a p99 added-latency budget under 20-30ms excluding safety models — run heavy classifiers async-parallel with fast deterministic checks inline.

## How Industry Implements This

The 2026 gateway market has settled into clear niches: LiteLLM as the open-source standard (self-hosted, 100+ providers behind an OpenAI-compatible endpoint) for teams wanting control; Portkey for managed production routing with prompt/model-aware observability and guardrails; Kong AI Gateway for enterprises already on Kong's API platform (plugin ecosystem, SSO, PII redaction — see the [Kong AI Gateway guide](../platforms/08-kong-ai-gateway-guide.md) and [Kong + Entra ID integration](../platforms/09-kong-entra-id-integration.md)); Cloudflare AI Gateway for near-zero-setup edge caching. Field heuristic: greenfield AI-only goes LiteLLM/Portkey, an existing API-platform estate gets extended, results-today favors managed edge.

In managed platforms, Azure AI Foundry Agent Service issues an Entra identity per agent — agent as first-class directory principal. AWS AgentCore Identity provides workload identity plus credential brokering, with AgentCore Gateway holding tool credentials server-side so agents never see them — the secrets doctrine above, delivered as a managed service. In financial services, banks apply the RBAC-to-risk composite directly: A2A internal agent directories at scale for trade reconciliation and KYC, dual control on funds-adjacent pivot steps, and full decision replay for SR 11-7/DORA evidence — the PDP decision log is the regulator artifact. Gateways are also absorbing the tool side: MCP gateways route on the 2026-07-28 `Mcp-Method`/`Mcp-Name` headers without body parsing, and production operators report the gateway-plus-registry combination does most of the real work of agent governance.

## Architect's Checklist

- [ ] Idempotency keys on every mutating tool call; compensations registered per step; pivot points approval-gated and placed late
- [ ] Consistency model documented and promised (read-your-writes in-task, eventual across agents)
- [ ] Identity chain verifiable end-to-end: OIDC human anchor to attested workload identity to narrowing sub-agent delegation to audience-bound tool tokens
- [ ] No token passthrough anywhere; RFC 8707 resource indicators on all MCP tokens
- [ ] All tokens ≤15 min, sender-constrained (DPoP/mTLS-bound) across network hops
- [ ] Delegation grants stored as first-class objects; STS consults them at mint time
- [ ] Policy layering enforced: platform invariants non-overridable; lower layers restrict only
- [ ] Every PDP decision logged with policy bundle hash — replayable for audit
- [ ] One AI gateway on the path of all model traffic; virtual keys; provider creds only in the gateway
- [ ] Prompt provenance tags on every context segment
- [ ] Gateway p99 added latency < 20-30 ms; heavy classifiers async
- [ ] Per-tenant cache scope keys; no cross-tenant batching
