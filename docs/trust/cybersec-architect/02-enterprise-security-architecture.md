Security architecture taught from an Enterprise Architect perspective, spanning the Business, Information, Application, and Technology layers of the architecture stack — using SABSA and TOGAF's Security Architecture extension to position security as a governed business capability, not a technology function.

## Security as an Enterprise Capability

Security is not a technology function — it's a business capability that must be designed, funded, measured, and governed like any other capability in the enterprise portfolio. Every business capability carries a corresponding security requirement: customer data processing needs classification/encryption/DLP/privacy controls; employee productivity via SaaS needs identity governance/CASB/endpoint DLP; AI-powered products need AI security controls/prompt gateway/model governance; third-party integrations need an API security gateway/OAuth/supply-chain risk management; remote/hybrid work needs ZTNA/device posture/phishing-resistant MFA; cloud infrastructure needs CSPM/CWPP/cloud IAM/network segmentation; software development needs DevSecOps/SCA/secret scanning/SBOM; financial transaction processing needs PCI DSS controls/HSM/tokenization/fraud detection. Every new business capability introduced by digital transformation or AI adoption carries a corresponding security capability requirement that must be identified, designed, funded, and operated.

## Business Layer

The starting point for enterprise security architecture is the business capability map, with security capabilities mapped onto that foundation. A Level 1 security capability map spans six domains: Risk Management (cyber risk quantification, third-party risk management, risk reporting/governance); Identity & Access Management (human, machine, and AI agent identity); Data Protection (classification/governance, encryption/key management, privacy/sovereignty); Threat Management (vulnerability management, threat intelligence, security monitoring/response); Security Engineering (secure architecture design, DevSecOps, AI security engineering); and Governance, Risk & Compliance (policy management, compliance assurance, audit/assurance).

The security operating model defines how these capabilities are organized, staffed, funded, and governed across five dimensions: structure (centralized, federated, or hybrid — driven by org size, regulatory environment, risk appetite); ownership (CISO-led, CTO-embedded, or distributed — driven by culture, transformation maturity, board mandate); sourcing (insourced, MSSP, or hybrid — driven by cost, skill availability, 24x7 requirements); governance (a security council, ARB-integrated, or a dedicated risk committee — driven by regulatory requirements and the enterprise governance model); and funding (cost center, risk-adjusted allocation, or business-unit chargeback — driven by the finance model and board risk appetite). With AI agents acting on the enterprise's behalf, the operating model must add AI governance roles — AI Security Engineer, AI Red Team Lead, Model Risk Officer — alongside traditional security roles.

Business resilience is the program's ultimate outcome, measured via Recovery Time Objective (maximum tolerable downtime per capability), Recovery Point Objective (maximum tolerable data-loss window), MTTD, MTTR, and a composite cyber resilience score combining control effectiveness, detection speed, and recovery capability. Cyber risk management follows the basic identity Risk = Threat × Vulnerability × Impact, quantified via FAIR (quantitative financial loss modeling), NIST CSF (qualitative maturity across Identify/Protect/Detect/Respond/Recover/Govern), ISO 31000 (enterprise risk integration), and COSO ERM (board-level business risk integration) — with AI adding model failure risk (hallucination, misalignment), agent autonomous-action risk (unintended real-world effects), AI supply-chain risk (third-party model or data compromise), and regulatory AI risk (EU AI Act, ISO 42001 non-compliance).

A CMMI-based security maturity model spans five levels: Initial (ad hoc, reactive, no defined processes); Managed (basic processes exist, mostly reactive); Defined (documented, consistent processes across the organization); Quantitatively Managed (metrics-driven, risk quantified, predictive); Optimizing (continuous improvement, automation, AI-assisted). Most enterprises target Level 3 for foundational domains and Level 4 for critical capabilities — AI security is a new domain where most enterprises sit at Level 1-2 as of mid-2026.

## Information Layer

Data classification is the foundation of information security — without knowing what's sensitive, no proportionate controls can be applied. A standard five-tier scheme runs Public (freely shareable — marketing materials), Internal (employees only — policies, org charts), Confidential (restricted access — financial forecasts, roadmaps), Restricted (need-to-know — customer PII, trade secrets, source code), and Regulated (subject to legal obligations — PHI/HIPAA, cardholder data/PCI, biometrics). AI introduces new classification challenges: training datasets may mix classification levels, LLM outputs may synthesize restricted information from public inputs, RAG pipelines mix document sensitivity levels within a single context window, and agent memory stores accumulate sensitive data across sessions.

The CIA triad extends into the AI era: confidentiality's traditional controls (encryption, access control, DLP) extend to prompt-injection prevention, output filtering, and RAG access control; integrity's traditional controls (checksums, digital signatures, audit logs) extend to training-data integrity, model-card verification, and AIBOM attestation; availability's traditional controls (redundancy, DDoS protection, BCP) extend to model-serving resilience, inference rate limiting, and fallback model chains.

Privacy by design, a sub-property of confidentiality with legal consequences, follows Ann Cavoukian's seven principles: proactive not reactive; privacy as the default setting; privacy embedded into design; full functionality (positive-sum, not zero-sum); end-to-end security lifecycle protection; visibility and transparency; and respect for user privacy. AI-specific privacy risks include membership inference (can an attacker determine if a specific person's data was in the training set), model inversion (can training data be reconstructed from model outputs), re-identification (can anonymized data be re-identified using AI), and consent scope (was data used for AI training within the consent originally given).

Data sovereignty requires data be subject to the laws of the nation where it resides: EU GDPR applies to EU residents' personal data regardless of processing location; the EU AI Act adds obligations for high-risk AI systems using EU citizen data; US federal and defense workloads often require FedRAMP-authorized, US-data-only processing; and cross-border AI (LLMs hosted outside the EU processing EU personal data) triggers SCCs and transfer-mechanism requirements. AI data governance must span the full lifecycle: consent and minimization at collection, classification and labeling at curation, lineage and provenance through training, change control through fine-tuning, request logging at inference, content filtering on output, and deletion/purging at retention's end.

## Application Layer

Secure application architecture rests on eight principles: least privilege (request only needed permissions per operation); defense in depth (multiple independent controls per layer); fail secure (deny on error, don't grant); input validation at trust boundaries; output encoding to prevent injection; secure defaults (the default configuration is the most secure one); separation of concerns (security logic separate from business logic); and audit by design (security-relevant events logged from design time).

APIs are the primary integration surface of modern applications and the attack surface for AI agents. Controls layer as: authentication (OAuth 2.1/OIDC/mTLS verifying caller identity); authorization (RBAC/ABAC/OPA policies controlling what a caller can do); rate limiting (API gateway policies preventing abuse and DDoS); input validation (JSON Schema/OpenAPI spec rejecting malformed requests); output filtering (response sanitization preventing data leakage); threat protection (WAF/API security gateway blocking known patterns); and logging/monitoring (structured API logs into SIEM detecting anomalies). AI agent-specific additions: short-lived, least-privilege per-task token scoping; tool-invocation audit trails per agent session; rate limiting per agent identity rather than only per IP; and semantic validation of AI-generated API calls.

Event-driven architectures introduce their own patterns: topic-level access control requiring explicit producer/consumer authorization per topic; event poisoning risk, where malicious events injected into streams (Kafka, EventBridge) trigger unintended downstream actions; schema enforcement preventing malformed payloads; event-replay audit trails restricting who can initiate a replay; and a requirement that events consumed by AI agents be classified before processing.

Service meshes (Istio, Linkerd, Consul) provide automatic mTLS between microservices with no application code changes, SPIFFE/SPIRE workload identity via cryptographic attestation (detailed in [Part 6](06-identity-architecture.md)), L7 policy enforcement (JWT validation, path-based authorization) at the proxy layer, and distributed tracing/access logging for every service call. Agents deployed as microservices can participate directly in the mesh, gaining automatic mTLS and workload identity without embedding API keys in the agent runtime.

The Model Context Protocol (MCP) is the emerging standard for AI agent tool integration: an MCP client (the agent) authenticates to an MCP server (the tool) via OAuth 2.1, with the agent's identity established via SPIFFE SVID or an Entra token and the server enforcing per-tool, per-resource ACLs. MCP security controls: server authentication before any tool invocation; per-tool permission scoping; tool output validation before the agent processes it; full audit logs of every call (agent ID, tool, parameters, result); and rate limiting per agent per tool. See [MCP & A2A Protocol Deep Dive](../../architecture/58-mcp-a2a-protocol-deep-dive.md) for the full specification.

The prompt gateway is a security-as-infrastructure layer sitting between AI consumers and the underlying model: it handles authentication/authorization, input filtering (PII, injection patterns, jailbreak detection), rate limiting and cost controls, model routing (primary/fallback), output filtering (toxicity, PII, hallucination detection), audit logging, and governance policy enforcement, before the request ever reaches the LLM API. See [Part 13's reference implementation](13-security-patterns.md) for the full pattern.

## Technology Layer

Network security technologies span segmentation (software-defined microsegmentation — Illumio, Guardicore), ZTNA (Zscaler ZPA, Cloudflare Access, Netskope, replacing VPN with identity-aware access), SASE (converging SD-WAN and SSE — Palo Alto Prisma, Zscaler, Cisco+), NGFW (L3-L7 filtering — Palo Alto, Fortinet, Check Point), and DDoS protection (Cloudflare Magic Transit, AWS Shield Advanced).

Kubernetes, the dominant orchestration platform, needs controls at every layer: the API server (RBAC, admission controllers, audit logs via OPA Gatekeeper/Kyverno); nodes (CIS Benchmark hardening, immutable OS via Bottlerocket/Flatcar); pods (security contexts, no root, read-only filesystem via Pod Security Standards); network (network policies and mTLS via Cilium/Calico/Istio); images (signed images and vulnerability scanning via Cosign/Trivy/Snyk); secrets (external secrets operators, no env-var secrets via Vault/AWS SSM); and runtime (syscall filtering and anomaly detection via Falco/Sysdig).

Confidential computing keeps data encrypted even during processing: Intel TDX and AMD SEV-SNP provide VM-level memory encryption; AWS Nitro Enclaves, Azure Confidential VMs, and Google Confidential VMs provide isolated compute for sensitive processing. AI use cases include private inference (customer data never leaves encrypted memory during LLM inference), confidential fine-tuning (training on sensitive data without exposure to the cloud provider), and secure multi-party computation (collaborative model training without data sharing). Hardware security underpins all of this: TPM 2.0 provides platform attestation and key storage for device-health verification in Zero Trust; HSMs handle cryptographic key generation/storage/operations for PKI and encryption; Secure Boot verifies firmware integrity against bootkits; and secure enclaves (Intel SGX, ARM TrustZone) provide isolated execution environments for sensitive AI inference without host OS access.

Software supply-chain attacks (SolarWinds, Log4Shell, XZ Utils) have elevated supply-chain security to a board-level concern. Controls: an SBOM inventories all software components and dependencies; an AIBOM inventories model components, training-data sources, and inference dependencies; Sigstore/Cosign provide cryptographic signing of software artifacts; SLSA provides a framework for build provenance and integrity; Dependency-Track provides automated vulnerability monitoring for SBOM components; and private artifact registries remove direct public-registry access from production entirely.
