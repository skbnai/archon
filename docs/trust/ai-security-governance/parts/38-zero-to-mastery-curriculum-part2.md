Stages 2-4 (Weeks 3-5): Identity & Non-Human Identity, MCP Security, and A2A Security — the program's core stack, closing with the Phase II Capstone.

## Phase II: The Core Stack

Stages 2 through 4 are the heart of this program. Identity, MCP, and A2A are presented as three separate stages, but by Stage 4 you should see them as one continuous trust chain — identity establishes who's acting, MCP governs what tools they use, A2A governs how they trust each other. This phase corresponds to [Identity/MCP/A2A Security Blueprint](../34-identity-mcp-a2a-security-blueprint.md) and its [MCP Security](../parts/34-identity-mcp-a2a-security-blueprint-part2.md) and [A2A Security](../parts/34-identity-mcp-a2a-security-blueprint-part3.md) parts.

## Stage 2 (Week 3): Identity & Non-Human Identity (NHI)

This is, by a wide margin, the highest-leverage stage in the curriculum: if an organization can fund only one part of this program, fund the identity substrate. Everything from here forward — MCP gateways, A2A trust, governance reporting — gets dramatically easier once every agent carries a verifiable, ephemeral, centrally governed identity, and harder if it doesn't.

**By the end of this stage, you will be able to:** explain why static API keys and shared service accounts are inadequate for agent populations; describe how SPIFFE/SPIRE issues workload identity, including attestation and what an SVID proves; explain SPIFFE's core limitation (it authenticates the workload, not the intent); design a compound identity model distinguishing "which agent" from "on whose authority"; and compare delegation patterns (service accounts, OAuth On-Behalf-Of, RFC 8693 token exchange, impersonation).

*Prerequisite check: comfortable with Stage 0's AAA distinction and Stage 1's credential-custody pattern — this stage answers the question Stage 1 left open.*

Most organizations have solved "can this agent prove it's the agent it claims to be" using static API keys or shared service accounts — which authenticates something, but creates standing, long-lived, broadly-scoped credentials sitting in configuration files, exactly the asset an attacker or a manipulated agent wants to find. The harder, mostly unsolved problem is authorization: not "who is this" but "what should this agent be allowed to do, right now" — the gap between those questions is where almost every real agent-identity incident lives. Human identity (log in once a day) and server identity (stable for months) both assume relative stability agents don't share: they're ephemeral, they proliferate rapidly, and a single agent's blast radius can span many systems in one session.

SPIFFE (Secure Production Identity Framework For Everyone) issues cryptographic identity to workloads rather than humans; SPIRE is the reference implementation. A local SPIRE agent observes properties of a starting process — its Kubernetes service account, container image, cloud instance metadata — against registered selectors, and if they match, issues a short-lived SVID (SPIFFE Verifiable Identity Document), typically an X.509 certificate. Two SPIFFE-identified processes then establish mutual TLS directly, without a shared secret or manual enrollment. An agent spun up seconds ago, never manually registered, can prove cryptographically which legitimate process it is — and that proof expires and re-issues continuously rather than sitting as a static secret.

**The limitation you must hold onto:** an SVID proves "this is the legitimate agent process running this container image." It proves nothing about what that process is about to do next. SPIFFE authenticates the workload, not the intent — the Stage 0 authentication/authorization distinction reappearing in its most consequential form. A perfectly authenticated agent can still be the agent doing something it shouldn't.

Most real agent actions happen on behalf of someone or something else: a human user, a business process, a delegating agent. The authorization decision must account for both "which agent" (SPIFFE answers this) and "on whose authority is it acting right now" (SPIFFE does not). An agent with a valid SVID acting for a now-suspended user account should be blocked, but a workload-identity check alone can't know that. The answer: carry both pieces together as a structured claim — commonly an "actor" claim inside a JWT, following the RFC 8693 Token Exchange pattern — so every downstream system sees, in one place, which agent is acting and on whose authority.

Delegation patterns compared: **Service Accounts** are static, shared, non-human credentials — acceptable only for the lowest-risk automation. **OAuth On-Behalf-Of** carries a human's authorization through a service chain — fine for shallow delegation but strains under deep multi-agent chains. **RFC 8693 Token Exchange** is the recommended default for agent-acts-for-user flows, still maturing in adoption. **Federated Identity** gives cross-domain trust without a shared credential store, but federation agreements were built for human SSO cadence, not agents discovering new counterparties at runtime. **Impersonation** — the agent assumes the user's full identity — should be avoided by default: it destroys the audit distinction between "the user did this" and "the agent did this for the user."

**Hands-on lab: design a compound identity token.** Continuing the customer support agent from Stage 1: it now drafts and, after human approval, sends email replies on behalf of the support team — sometimes ticket-triggered, sometimes explicitly invoked by a human. Sketch a token (simple JSON) capturing both the agent's workload identity and the principal it's acting for; show three scenarios where its claims change shape (autonomous, human-invoked, suspended account); write the downstream authorization rule as plain-English if/then, stating what happens if the acting-for principal is suspended even though the SVID is valid; and identify which delegation pattern is the wrong choice here and why. **Deliverable:** the token sketch (3 variants), the authorization rule, and the pattern justification.

**Knowledge check:** (1) Explain what workload attestation checks without using the term "SPIFFE," and why that differs from trusting whatever credential shows up. (2) A teammate says "our agents all have valid SVIDs, so we know exactly which agent is doing what — we don't need authorization logic." What's wrong here? (3) Why is impersonation worse than a compound identity token, even though both let the agent "act as" the user? (4) Describe a scenario where RFC 8693 token exchange fits better than plain OAuth On-Behalf-Of.

## Stage 3 (Week 4): Model Context Protocol (MCP) Security

MCP is how an agent talks to tools — and, as of 2026, the most actively exploited layer in the agentic stack, with research showing a majority of public MCP servers carry at least one serious flaw class. This stage applies the credential-custody and identity foundations from Stages 1-2 to the live MCP threat landscape.

**By the end of this stage, you will be able to:** explain MCP's protocol basics (JSON-RPC, SSE vs. STDIO transport) and where each transport's biggest risk lives; identify tool poisoning, spoofing/rug pulls, dynamic tool escalation, tenant escape, and schema manipulation as distinct threats; explain why discovery-time validation alone is insufficient and design a two-gate (discovery plus invocation) approach; build a working gateway policy enforcing allowlisting, schema validation, and identity-based authorization; and evaluate an MCP server against a security checklist.

*Prerequisite check: comfortable with credential custody (Stage 1) and compound identity (Stage 2) — MCP gateway design assumes both.*

MCP standardizes how an agent discovers and calls external tools, built on JSON-RPC 2.0 over one of two transports: STDIO (a local subprocess, inheriting the privilege of whatever runs it — common for IDE-integrated assistants) or SSE/HTTP (a remote server shared across an organization). The specification leaves much of authentication and session-handling up to whoever implements a given server, the root cause of most of what follows.

Five attack patterns to recognize on sight: **Tool Poisoning** — a tool's description, read by the agent as reasoning context but rarely seen by a human, contains hidden instructions; "fetch data from S3" can also invisibly instruct exfiltration elsewhere. This is MCP's instance of "content becomes instructions" from Stage 1. **Tool Spoofing / Rug Pulls** — a malicious server registers a tool with a name nearly identical to a legitimate one, or a reviewed tool is silently modified post-installation, so a point-in-time review gives no durable guarantee. **Dynamic Tool Escalation** — a broad tool granted for a low-risk task is reused later for a higher-risk action nobody approved. **Tenant Escape** — insufficient isolation in a multi-tenant server lets one tenant's agent read or influence another's session. **Schema Manipulation** — tool schemas are altered or under-validated, letting an agent pass malicious parameters the receiving system doesn't adequately check.

It's tempting to think "we scanned the tools before deploying, so we're covered" — this misses that a model with a clean, validated tool list can still be manipulated, at the moment it calls the tool, into supplying malicious parameters the original review never saw. The fix: gate twice, validating at discovery time and again at every invocation against the same schema.

The MCP gateway pattern applies Stage 1's "credentials live outside the agent" principle to tool access generally: route all MCP traffic through a centralized gateway rather than letting local configuration decide which servers to trust. Five gateway stages: discovery-time schema validation (every tool definition scanned for hidden-instruction patterns before reaching an agent's context); server allowlisting (only explicitly approved servers reachable); identity and transport enforcement (mTLS plus authenticated workload identity — where Stage 2's SPIFFE work plugs directly in); policy evaluation at invocation (every call re-checked against policy and the original schema); and tamper-evident audit logging (every allow, deny, and policy change logged with integrity protection).

**Hands-on lab: build a minimal MCP gateway policy.** Your organization has three internal MCP servers (CRM-read, knowledge-base-search, email-draft) and is onboarding a fourth, third-party calendar-scheduling server. Write an allowlist policy naming the four servers and their approved tools; for the third-party server, list the additional checks that don't apply to the internal three; design the invocation-time re-validation rule for the email-draft tool, including the decision if a recipient was never seen for this ticket before; and identify which gateway stage would catch a rug-pull where the calendar tool is silently modified weeks after approval to forward invites externally. **Deliverable:** the allowlist, third-party checks, the email-tool rule, and the rug-pull answer.

**Knowledge check:** (1) Explain tool poisoning versus tool spoofing, with an example of each. (2) Why isn't "we scanned every tool before deploying" sufficient to prevent tool poisoning? (3) A vendor claims their MCP server needs no gateway because it's "secure by design" — what would you ask? (4) Using the trust-boundary concept from Stage 0, why is a multi-tenant MCP server higher-risk than a single-tenant one with identical tool definitions?

## Stage 4 (Week 5): Agent-to-Agent (A2A) Security

Where MCP governs agent-to-tool trust, A2A governs agent-to-agent trust — increasingly across organizational boundaries, with more than 150 production organizations on Google's A2A protocol as of 2026. This stage closes Phase II by extending identity and gateway patterns to a counterparty that isn't a tool you control, but another autonomous agent you may not.

**By the end of this stage, you will be able to:** explain Agent Cards, discovery, and Signed Agent Cards (A2A v1.0); identify card poisoning, spoofing/forgery, agent-in-the-middle, and rogue/compromised trusted agents as distinct threats; explain why a previously trustworthy agent is the most dangerous A2A threat actor; design an A2A gateway with discovery validation, claims mapping, and a trust broker; and explain what A2A's cryptographic guarantees don't cover.

*Prerequisite check: comfortable with the MCP gateway pattern (Stage 3) and compound identity (Stage 2) — most of A2A security is the same pattern applied peer-to-peer.*

A2A, originated by Google and now governed by the Linux Foundation under neutral, multivendor stewardship, lets agents discover, communicate, and collaborate as peers across organizational and framework boundaries. Discovery works through Agent Cards: structured documents an agent publishes describing what it can do, what authentication it expects, and where to reach it. A host agent incorporates Agent Cards into its own planning when deciding whether to delegate a task — recalling the "content becomes instructions" risk from Stage 1, because that's exactly what's happening. Earlier A2A versions treated authentication as effectively optional; the biggest improvement, in v1.0, was Signed Agent Cards — a signature tied to the publishing domain, so a receiving agent can verify a card came from the domain it claims. Signing is supported by the spec, not enforced, so unsigned deployments remain vulnerable.

Four threats to recognize: **Agent Card Poisoning** — malicious instructions embedded in a card's metadata, incorporated into a host agent's planning context; research demonstrates this causing unintended transmission of sensitive data in a simulated booking scenario. **Agent Card Spoofing / Forgery** — a fake card at an attacker-controlled domain, redirecting peers to a malicious endpoint, mitigated but not eliminated by Signed Agent Cards. **Agent-in-the-Middle** — an intermediary intercepts and manipulates A2A traffic between legitimate peers. **Rogue / Compromised Trusted Agents** — a legitimately onboarded, previously well-behaved agent is later compromised, and its trust is exploited precisely because a clean record makes detection less likely — the most operationally dangerous of the four.

The enterprise A2A gateway mirrors the MCP gateway pattern for peer-to-peer trust: discovery validation (every inbound card cryptographically verified against its signature; unsigned cards rejected by default); claims mapping (an external agent's claimed authority is bounded by internal policy, never trusted at face value); a trust broker (tracking trust relationships and scores for every known counterparty); policy evaluation (every delegated task checked against budget limits, data-sensitivity boundaries, and allowed task types); and audit logging tied to the compound identity of both sides.

Signing Agent Cards and using mutual TLS secures a message's integrity and authenticity — it proves the message came from who it claims and wasn't tampered with in transit. It does nothing to prevent an agent from being validly manipulated into a bad decision, the way prompt injection manipulates a single agent. A cryptographically perfect, fully authenticated delegation to do something harmful is still harmful.

**Hands-on lab: design an A2A trust broker decision.** Your support agent now delegates shipping-status checks to an external logistics partner's agent via A2A. Write the discovery-validation check your gateway performs on the partner's card before any delegation; design a trust-score model (0-100 or tiered) with at least three signals; write the policy rule for what score is required before sending shipping address and order ID, and what happens if the score drops mid-relationship; and describe a card-poisoning scenario specific to this relationship and which gateway function defends against it. **Deliverable:** all four points as a design document.

**Knowledge check:** (1) Why do Signed Agent Cards reduce, but not eliminate, A2A's spoofing risk? (2) Why is a previously-trustworthy rogue agent more dangerous than an obviously malicious new one, and what does that imply for how trust scores should behave over time? (3) A colleague argues mTLS plus signed cards makes the system secure — what's the gap, and what Stage 1 concept explains it? (4) Sketch what "claims mapping" does differently than trusting whatever authority an external card claims for itself.

**Phase II Capstone: The Unified Trust Chain.** Extend your Phase I architecture sketch into a complete identity-to-trust design covering Stages 2-4: a compound identity design for every agent, including issuance and contents; a complete MCP gateway policy for every tool used, including the two-gate pattern; a full A2A gateway design if the system has any plausible cross-organization interaction — if not, a one-paragraph justification plus a forward-looking design for a hypothetical partner integration; and a paragraph explaining, end to end, how identity flows from Stage 2 through the MCP gateway and, if applicable, the A2A gateway, demonstrating one continuous chain rather than three separate topics. **Graded against:** whether identity is treated as the substrate everything else builds on, and whether the two-gate MCP and trust-broker A2A patterns are correctly reasoned, not just named.
