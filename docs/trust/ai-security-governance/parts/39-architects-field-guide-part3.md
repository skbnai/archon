Meridian Trust Bank, weeks 10-19: standing up the AI SOC's seven-surface correlation logic, drilling the kill switch, and the live incident that tests all of it at 2 a.m.

**Fictionalization note:** Meridian Trust Bank and this engagement are fictional, composited from realistic patterns. Every technical mechanism and tradeoff described is grounded in the same 2026 material underlying the rest of this program.

## Chapter 5: Standing Up Operations

*Weeks 10-16.*

By week ten, Meridian has an identity substrate, a consolidated MCP gateway, a working A2A integration, a chartered governance board, and a documented autonomy-classified fleet. None of that tells anyone whether the system is behaving correctly at 2 a.m. on a Tuesday. This chapter builds the watching function — and it matters enormously for Chapter 6, because the incident that follows is only caught, contained, and correctly diagnosed because of choices made here.

**Decision Point: which observability platform, and how much do you build versus buy?** Meridian's engineering organization already runs Datadog for conventional infrastructure observability, with significant existing investment and institutional knowledge; none of the agent-specific platforms (LangSmith, Langfuse, Arize Phoenix) are yet in use anywhere in the bank. Three options: adopt LangSmith fully, separate from Datadog (best native integration if the bank standardizes on LangGraph, but creates a second monitoring pane of glass the existing SOC team would need to separately learn); self-host Langfuse as a fully independent stack (full data sovereignty and no vendor lock-in, but highest initial build effort and ongoing operational ownership for an already-stretched team); or **instrument every agent with OpenTelemetry/OpenLLMetry conventions and feed traces into the existing Datadog pipeline** (leverages the SOC team's existing tooling immediately, at the cost of building agent-specific dashboards and detection logic on top of Datadog rather than getting them out of the box). The third was chosen.

**Rationale:** the deciding factor wasn't which platform has the best agent-specific features in isolation — it was that Meridian already has a 24/7 SOC team trained on Datadog, and asking them to also learn a separate platform for agent traffic would mean agent security incidents got slower, less experienced eyes during exactly the hours (nights, weekends) when fast triage matters most. The OpenTelemetry layer keeps agent traces vendor-portable for the future while getting agent visibility in front of the team with 24/7 coverage on day one.

**Building the seven-surface correlation logic.** Meridian's detection logic was built to watch seven surfaces — but not all simultaneously; engineering capacity required sequencing, and the sequencing choice mattered a great deal in Chapter 6. Identity was built first (weeks 10-11): it directly extended the Chapter 2 SPIFFE work and was cheapest to instrument, since attestation and token-exchange logs already existed. MCP was second (weeks 11-12): the gateway was already centralized, with logs already structured and consistent. Memory was third (weeks 12-13): it required new instrumentation at every memory write path across the fleet, the most labor-intensive surface to build. A2A was fourth (week 13): only one production external counterparty existed at this point, so detection logic was deliberately built thin and well-tested rather than broad. Runtime was fifth (weeks 14-15): sandbox telemetry from Firecracker/gVisor environments required platform engineering coordination outside the security team's direct control. Agents/behavioral (goal conformance) was sixth (week 15): it required the ARE SLI work to mature first before behavioral baselines were meaningful. Guardrails was seventh (week 16), lowest priority, since Meridian hadn't yet deployed a dedicated guardrail platform — the least mature surface at the time of the Chapter 6 incident, a fact that becomes directly relevant.

**The Architect's Reasoning.** Flag this sequencing, because it matters in the next chapter in a way that's easy to miss on a first read: memory was built third, ahead of A2A and well ahead of behavioral monitoring. That wasn't arbitrary — memory write paths touch customer PII directly, and the team correctly judged that the highest-consequence gap to close early. But it means that by the Chapter 6 incident, the bank had roughly five weeks of mature memory-surface monitoring against only about one week of behavioral/goal-conformance monitoring. Sequencing decisions like this are never free — they trade an earlier, stronger defense on one surface against a later, weaker one on another, and a good architect can usually predict, in advance, roughly where the resulting gap will bite first.

**Exhibit — AI SOC correlation rule CORR-014** ("unusual tool-call burst followed by unfamiliar memory write"), written for the customer support agent, the rule that ends up mattering in Chapter 6:

```yaml
rule_id: CORR-014
surfaces: [mcp, memory]
condition:
  - mcp.tool_calls.count(window=2m, agent=$AGENT) > baseline_p99 * 3
  - AND memory.write.entity_novelty(window=5m, agent=$AGENT) == "high"
  - AND identity.actor_claim.acting_for NOT IN recent_task_context($AGENT)
severity: HIGH
action: page_on_call, do_not_auto_kill  # human triage required before kill switch
```

The `do_not_auto_kill` flag was a deliberate, debated decision: this pattern can also occur during entirely legitimate bulk operations (a mass ticket reassignment during a reorganization), so the team chose human triage over automatic containment for this rule specifically, while other, higher-confidence rules elsewhere were configured to auto-kill. Knowing which rules deserve automatic response and which deserve a human in the loop first is an architectural judgment call, not a default to apply uniformly.

**Making the kill switch real, not theoretical.** The kill-switch framework existed on paper since Chapter 2 (revocation was always going to invalidate SVIDs and outstanding tokens), but "existing on paper" and "tested under realistic conditions" are different things. Week 16 included Meridian's first full drill: deliberately revoking the customer support agent's identity mid-session during a controlled test window, timed end to end. Time from trigger to SVID revocation propagating: 41 seconds, against a target set afterward of under 30. Time for in-flight tool calls to be rejected post-revocation: immediate. Time for queued-but-not-yet-executed tasks to be confirmed halted: 4 minutes 12 seconds, the worst result of the drill, and it became the top action item — target set at under 1 minute.

**Field Note.** The four-minute gap on queued task halting traced to a task queue built, reasonably, for reliability — designed to keep retrying a task through transient failures, exactly the right default for normal operations and exactly the wrong default the moment a kill switch fires. The fix (a kill-switch-aware queue checking revocation status before each retry, not just before initial dispatch) is unglamorous infrastructure work, and precisely the kind of gap a kill-switch framework that only ever exists on paper, never drilled, would have left undiscovered until a real incident found it the hard way.

## Chapter 6: The Incident

*Week 19, a Tuesday, 02:14 local time.*

Five months in, with the identity substrate, MCP/A2A gateways, governance board, and a young but real AI SOC all operating, the customer support agent — built across Chapters 2 through 5, the bank's single most heavily governed agent — is the one that gets hit. This isn't a coincidence: it has the broadest legitimate tool access of any agent in the fleet (CRM read/write, knowledge-base search, email drafting), making it both the most heavily controlled agent at Meridian and, for exactly that reason, the most valuable target.

The attack begins with a support ticket, ordinary on its face, submitted through the bank's normal customer-facing channel by what is later confirmed to be a compromised but legitimate customer account. The ticket text is a routine-looking billing question. Embedded in it, invisible in the rendered view but fully present in the raw text the agent processes, is an injected instruction.

**The Architect's Reasoning.** This is not a sophisticated zero-day against any piece of infrastructure built in Chapters 2 through 5 — the identity substrate, the MCP gateway, and the A2A trust broker all perform exactly as designed throughout. It is exactly the risk named as foundational from the start: untrusted content, in a channel nobody had a reason to suspect, treated with the authority of a legitimate instruction. Every architectural investment made across this engagement raises the cost and lowers the blast radius of this kind of attack — none makes it impossible, and a good architect never claims otherwise.

**The timeline.** T+0:00 — the compromised account submits a ticket containing an indirect prompt injection, formatted to resemble metadata the ticket system legitimately attaches to billing inquiries. T+0:03 — the ticket-triage agent (L2 bounded autonomy) processes it; the injected instruction directs it to "verify account linkage" for several other account numbers embedded in the text, framed as a routine duplicate-ticket-detection step. T+0:04-0:09 — the agent issues nine CRM read calls in rapid succession for the embedded account numbers, all within its granted scope, so no gateway policy is violated; each call is individually authorized. T+0:09 — CORR-014 fires: the tool-call burst exceeds baseline on the MCP surface, severity HIGH, `do_not_auto_kill` pages the on-call analyst. T+0:11 — the on-call analyst (a Tier 1 analyst cross-trained on agent monitoring; the dedicated AI SOC specialist had been hired but hadn't started yet) reviews the alert; the burst superficially resembles the legitimate bulk-reassignment pattern the rule's triage guidance was designed to tolerate, and marks it likely benign per the documented, in hindsight too-permissive, guidance. T+0:14 — the agent, still acting on the injected instruction, drafts an email within its `email:draft` scope, addressed to an external address absent from the original ticket or any of the nine queried accounts' on-file contacts, containing a summary of account details framed as a "compliance verification export." Because the agent operates at L2, the email is held in draft state pending the human-approval gate — it does not send automatically. T+0:15 — a second alert fires, not from the still-immature behavioral surface, but from the memory-surface monitoring built in weeks 12-13, flagging that the draft's content referenced customer entities with no prior co-occurrence in this agent's session history — the same entity-novelty signal CORR-014 used, now firing independently on a different, higher-confidence rule. T+0:17 — this alert routes to a more experienced on-call engineer, who, seeing two independent surfaces implicating the same agent and session within 15 minutes, escalates immediately rather than re-triaging from scratch. T+0:19 — the kill switch is invoked manually; SVID revocation propagates in about 35 seconds, consistent with the Chapter 5 drill; the draft email, never sent, is quarantined, not deleted, preserving it as forensic evidence. T+0:24 — you're paged as the escalation point for any off-hours kill-switch invocation.

**The Architect's Reasoning: why the first analyst's stand-down wasn't a simple mistake.** It's tempting to focus on the four minutes between the first stand-down (T+0:11) and the second alert (T+0:15) as the story — but that framing misses the lesson. The first analyst applied the triage guidance correctly, as written, and the guidance hadn't yet been refined with enough real incident history to distinguish the legitimate bulk-reassignment pattern from this one. This is precisely the cost of the Chapter 5 decision to build behavioral monitoring last: with only about a week of baseline maturity, the system didn't yet have a confident signal for "this agent doesn't normally email never-before-seen external recipients" — exactly the signal that would have made the first alert unambiguous. The memory-surface rule caught it anyway, four minutes later, precisely because memory was built third instead of sixth. The tradeoff named explicitly in Chapter 5 is the same tradeoff that determined how this incident actually unfolded.

**Containment and the first 24 hours.** The immediate crisis is over within thirty-five minutes of the first alert, but containment isn't root cause. First, confirm no email left the building — the quarantined draft plus the email infrastructure's own outbound logs confirm, independently of the agent's own audit trail, that nothing was sent. Second, determine blast radius — reviewing the nine CRM reads individually: which records were actually read, what fields were exposed to the agent's context, and whether any of the nine accounts show signs of specific targeting versus incidental sweep-up. Third, trace the injection's origin, working backward from the ticket through the compromised account, in coordination with the bank's existing fraud-operations team — AI-specific incident response explicitly hands off to, and works alongside, conventional fraud and account-security functions, not in isolation. Fourth, check every other agent for the same exposure — because the technique exploited a generic property (the ticket-triage agent trusting ticket metadata fields) rather than anything specific to this agent's configuration, two more agents are found with a structurally similar, though not yet exploited, gap.

**Decision Point: do you disclose, and to whom, before the investigation is complete?** By hour six, you have high confidence no data left the bank and a credible, not yet fully proven, hypothesis about the injection mechanism. Three options: wait for the complete investigation before any escalation (avoids alarming leadership with an incomplete picture, but risks the appearance of withholding information if a regulator later asks why a gap existed before disclosure); full public/regulatory disclosure immediately, before confirming blast radius (maximally cautious on timing, but risks disclosing inaccurate information that has to be corrected later — its own credibility cost); or **immediate internal escalation to the Risk Committee and Legal with a clearly labeled preliminary assessment, explicit confidence levels, and a committed follow-up timeline**, with external/regulatory disclosure deferred to Legal once blast-radius confirmation completes. The third was chosen.

**Rationale:** this generalizes well beyond Meridian — a security incident response function's job is to produce the most accurate picture possible, as fast as possible, and be explicit about confidence levels and what remains unknown, not to make the external-disclosure call itself. Internal escalation with honest uncertainty, on a fast clock, lets Legal and the Risk Committee make a well-informed disclosure-timing decision rather than one made for them by a technical team trying to also play lawyer. The credibility of the technical incident report depends on never overstating certainty to make the news sound more resolved than it is.

**Root cause.** Forty-eight hours of investigation produce a root cause with three contributing layers, typical of real incidents, which are rarely a single clean failure — usually a chain where any one broken link would have prevented or contained the outcome. **Cognitive/input handling:** the ticket-triage agent treated structured-looking metadata fields within ticket text as more trustworthy than free-text content, without that distinction being an explicit, reviewed design decision — it emerged informally from how the original prompt was written, long before this engagement began; no instruction-data separation control existed at this granularity within an already-untrusted channel. **Detection tuning:** behavioral monitoring, the last of seven surfaces built, didn't yet have a mature enough baseline to make the first alert unambiguous — a sequencing tradeoff made consciously in Chapter 5, which worked on the memory surface and would have worked faster with more weeks of behavioral maturity. **Triage guidance:** the `do_not_auto_kill` human-triage path for CORR-014 used guidance not yet refined against enough real alert history to distinguish this pattern from the legitimate case it was written to tolerate — an acceptable, even correct, initial choice given the information available when it was written, exposed as insufficiently refined only once a real incident tested it.

**Field Note.** None of the three contributing layers is "someone made an obvious mistake." Every one was a reasonable decision given the information available when it was made, and every one is exactly the kind of gap that only becomes visible under the pressure of a real, or realistically simulated, incident. A mature security program is not one where incidents stop happening — it's one that finds out about the gap from a contained, well-detected incident with no actual data loss, rather than from a regulator, a journalist, or a customer.
