## Compliance

Mapping OWASP LLM Top 10 to A2A exposure and primary control: LLM01 Prompt Injection maps to cross-agent injection, controlled via message signing and content-context separation; LLM02 Insecure Output Handling maps to tool output poisoning, controlled via schema validation and output guardrails; LLM03 Training Data Poisoning maps to memory poisoning, controlled via append-only memory and provenance; LLM04 Model DoS maps to swarm amplification, controlled via fanout limits and rate limiting; LLM05 Supply Chain maps to dependency attacks, controlled via SLSA L3, SBOM, and signed containers; LLM06 Sensitive Information Disclosure maps to cross-agent data leakage, controlled via DLP and data classification tags; LLM07 Insecure Plugin Design maps to unvalidated tool calls, controlled via schema validation and capability contracts; LLM08 Excessive Agency maps to excessive privileges, controlled via least privilege and JIT elevation; LLM09 Overreliance maps to blind tool execution, controlled via output validation and human gates; LLM10 Model Theft maps to agent runtime compromise, controlled via TEE, SLSA, and keeping model weights out of the agent container.

Regulatory requirements and controls by framework: PCI DSS v4 requires cardholder data flow only through authorized agents with a full access audit log and strong cryptography, met via data classification, PCI-isolated agent segments, HSM for crypto, and an immutable audit log. HIPAA requires PHI authorization, vendor BAAs, minimum-necessary access, and audit controls, met via OBO carrying clinical role context, PHI tokenization, vendor BAA, and a HIPAA audit log. GDPR requires a lawful processing basis, data minimization, a right to erasure, and cross-border transfer controls, met via purpose-limited OBO tokens, PII minimization in payloads, erasure propagation, and adequacy decisions for cross-region agents. The EU AI Act requires high-risk system obligations, transparency, and human oversight, met via agent risk classification, HITL gates, an audit trail, and conformity assessment. SOC 2 Type II requires access control, audit logging, change management, and incident response, met by the full control set in this guide plus automated evidence collection. ISO 42001 requires an AI management system, risk management, and documentation, met via the governance operating model, risk register, and policy documentation. DORA requires ICT third-party risk management, resilience testing, and defined RTO/RPO, met via agent SLOs, resilience testing, a third-party agent risk register, and multi-region failover. The NIST AI RMF requires Govern/Map/Measure/Manage functions, met via the governance operating model, threat model, behavioral monitoring, and incident response.

For all production agents, OpenSSF/SLSA requirements specify: SLSA Level 3 (hermetic builds, non-falsifiable provenance, build policy enforcement); an SBOM in SPDX or CycloneDX format published to the registry at build time and continuously scanned; Sigstore/Cosign keyless signing for all container images and Agent Cards; and vulnerability management with a fix SLA of 14 days for critical CVEs, 30 days for high, and 90 days for medium.

## A2A and Enterprise Platform Integration

Microsoft Entra ID integration: Entra Agent ID provides first-class non-human agent identity with Conditional Access policies applying directly to agents; the Microsoft OBO flow (v2 token endpoint) exchanges a user token for a downstream agent token; agents can trigger PIM just-in-time elevation requests for human approval; Azure RBAC roles assign to agent managed identities and get evaluated by OPA or Cedar; and Workload Identity Federation exchanges a SPIFFE SVID for an Entra access token.

AWS IAM and IAM Identity Center integration: an IAM Role per agent with role assumption via STS, and Web Identity for Kubernetes pods; cross-account access via STS AssumeRole with ExternalId, never long-lived cross-account keys; policy enforcement via Cedar through AWS Verified Permissions, IAM policy as guardrail, and SCPs for account-level boundaries; secrets via AWS Secrets Manager with automatic rotation, fetched by role rather than environment variable; and OBO via IAM Identity Center with custom attribute propagation for user context.

HashiCorp Vault is the recommended secrets broker for multi-cloud A2A: an agent authenticates via its SPIFFE SVID through Vault's SPIFFE auth method, receiving dynamic secrets (database credentials, API keys) that are short-lived (TTL matching task duration), auto-revoked on lease expiry, and fully audit-logged — eliminating the need for agents to hold any long-lived credential, since every credential is unique per invocation.

Kubernetes integration composes five components per agent pod: a SPIRE agent DaemonSet providing the SVID via a Unix socket; an OPA sidecar for local policy enforcement; a NetworkPolicy for L3/L4 isolation between agent namespaces; Pod Security Standards (Restricted) preventing privilege escalation; and a workload identity annotation enabling cloud API access without stored secrets.

## Architecture Decision Matrices

Core architecture decisions: centralized versus decentralized A2A — choose a central orchestrator when compliance requires a single audit point or coordination is complex, choose peer-to-peer when high autonomy and low inter-agent latency matter, but start central and federate by domain as scale grows. OBO versus service accounts — use OBO (RFC 8693) when user accountability and an audit trail are required, use service identity for background/scheduled tasks with no live user session; OBO should be the default with service accounts reserved for background work. OAuth versus mTLS/SPIFFE — use OAuth 2.1 for cross-domain and external partners, use mTLS plus SPIFFE within the same domain and infrastructure; recommend SPIFFE plus mTLS within a domain and OAuth across domains. JWT versus PASETO — JWT where wide ecosystem support is required, PASETO v4 where strict algorithm agility and type safety matter; recommend JWT with DPoP in existing ecosystems and PASETO for greenfield builds. OPA versus Cedar versus OpenFGA — OPA for general policy and Kubernetes integration, Cedar for AWS-native formal verification, OpenFGA for relationship graphs; recommend OPA for multi-cloud, Cedar for AWS-native, and OpenFGA for relationship-heavy problems. Static versus dynamic discovery — static only for critical stable agent pairs or emergency fallback, dynamic registry-based as the enterprise-scale default. Fail-open versus fail-closed — fail-closed for Tier 1-2 security-critical/regulated workflows, fail-open acceptable only for Tier 4 non-critical workflows where user impact of blocking is unacceptable. Isolated versus shared memory — isolated per agent by default, shared only within the same trust tier when cross-agent context performance matters. Centralized versus federated governance — a central governance board for small enterprises with high compliance needs, domain-federated for large multi-BU enterprises, generally recommending federation with central standards and global controls. Runtime versus pre-runtime policy evaluation — runtime evaluation for dynamic ABAC context, pre-compiled/cached evaluation for performance-critical static RBAC; recommend runtime for authorization and pre-runtime for capability checks.

Trust and security decisions carry firmer defaults: Agent Cards should always be signed with Ed25519, since unsigned cards are forgeable with no valid production justification — never override. Delegation depth should cap at 5 hops, since beyond that audit trails become unmanageable and confused-deputy risk grows exponentially — increase only with compensating real-time chain monitoring. Token lifetimes should hold at 1 hour for SVIDs, 15 minutes for access tokens, and 24 hours for refresh tokens, since these durations limit breach exposure without operational friction — decrease for Tier 1 agents, never increase. Registry trust should combine a registry CA with per-card signatures for defense in depth (a single card key compromise doesn't compromise the registry, and registry CA compromise requires re-signing all cards) — a single signature is acceptable only for small, low-risk deployments. mTLS for internal A2A should be mandatory, since there's no operational reason to skip it within enterprise infrastructure in 2026 — the only exception is legacy systems that can't participate, handled via gateway-terminated mTLS with a proxy.

## Appendix A: Enterprise Implementation Checklist

Identity and authentication: SPIFFE/SPIRE deployed with HA (3+ server nodes); every agent has a unique SVID (no shared identities); production SVID TTL under 1 hour; mTLS enforced on all A2A connections; DPoP-bound access tokens for OAuth flows; cross-cloud Workload Identity Federation configured; no static API keys or long-lived secrets in agent runtimes.

Authorization and delegation: an HA policy engine (OPA/Cedar) deployed; every A2A call authorized via the PDP, not agent-local checks; delegation depth capped at 5 hops; RFC 8693 token exchange implemented for OBO; scope attenuation enforced at every hop; delegation loop detection active.

Agent Cards and registry: every card signed with Ed25519 or ES256; dual-sign approval required for new registrations; schema validation enforced at registry ingress; a tested revocation mechanism; discovery gateway enforcing caller-based ACLs; card TTL capped at 1 year (shorter for high-risk agents).

Protocol and payload: TLS 1.3 enforced on all connections; nonce-based replay protection active; maximum payload size enforced at the gateway; JSON Schema validation at gateway ingress; correlation IDs propagated through the full chain; W3C traceparent propagated for distributed tracing; idempotency keys required for mutating operations.

Guardrails and sanitization: prompt injection detection on inter-agent messages; DLP scanning on cross-domain payloads; output guardrails for PII/sensitive content; HITL gates for irreversible Tier 1 actions; a delegation depth guardrail at token exchange; a fanout limit per orchestration chain.

Observability: OpenTelemetry tracing active on all agents and the gateway; a structured audit log for every call; authorization decision logging (allow/deny, reason, policy version); an agent interaction graph with active anomaly detection; SIEM integration for security events; active trust score computation and monitoring.

Governance: an agent onboarding workflow combining automated and human review; risk tier classification for all agents; published capability contracts for all declared capabilities; SBOM generated and published for all builds; SLSA Level 2+ (target 3) for production agents; a quarterly security review process for Tier 1-2 agents; a documented and tested deprecation/sunset process.

## Appendix B: Glossary

A2A (Agent-to-Agent protocol, the Google-donated, Linux Foundation-governed standard for inter-agent communication); ABAC (Attribute-Based Access Control); Actor token (the `act` JWT claim carrying the intermediate-service identity in RFC 8693 delegation chains); Agent Card (A2A's machine-readable descriptor of an agent's identity, capabilities, skills, and authentication requirements); Attestation (cryptographic proof a workload has specific measurable properties); Cedar (Amazon's formally-verifiable policy language backing AWS Verified Permissions); Confused deputy (a privilege-escalation pattern where a higher-privilege agent acts beyond a lower-privilege caller's authorization); DPoP (Demonstrating Proof of Possession, binding an OAuth token to a client's ephemeral key pair); Federation (a trust relationship between separate identity domains enabling cross-domain authentication without shared secrets); HITL (Human-in-the-Loop); JWT-SVID (a SPIFFE Verifiable Identity Document encoded as a JWT); Nonce (a cryptographically random value used once to prevent replay); OBO (On-Behalf-Of, the OAuth delegation pattern where an agent acts with a user's authorization while keeping its own identity); OPA (Open Policy Agent, the CNCF policy engine using Rego); OpenFGA (an open-source implementation of Google's Zanzibar ReBAC model); PASETO (a JWT alternative with constrained algorithms preventing common JWT vulnerabilities); PBAC (Policy-Based Access Control); PDP (Policy Decision Point); PEP (Policy Enforcement Point); ReBAC (Relationship-Based Access Control); RFC 8693 (the IETF OAuth 2.0 Token Exchange standard); SLSA (Supply-chain Levels for Software Artifacts, the OpenSSF supply-chain security framework); SPIFFE (Secure Production Identity Framework For Everyone, the CNCF workload identity specification); SPIRE (the CNCF reference implementation of SPIFFE); SVID (SPIFFE Verifiable Identity Document, issued by SPIRE in X.509 or JWT form); TEE (Trusted Execution Environment, e.g. AMD SEV-SNP, Intel TDX); Trust domain (a SPIFFE administrative boundary within which agents share a SPIRE CA); Workload Identity Federation (the cloud-native mechanism accepting external OIDC/SAML assertions in exchange for cloud-native credentials); Zanzibar (Google's internal ReBAC system, the design basis for OpenFGA).
