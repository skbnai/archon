## Chapter 10: OCI Runtime Specification and runc

The OCI Runtime Specification defines the interface between a container image (as an extracted filesystem bundle) and the container runtime. `runc` is the reference implementation — it is the component that ultimately makes the Linux system calls to create the container process.

### The Container Creation Sequence

Kubernetes → kubelet → containerd → runc → Linux kernel:

1. **API Server**: Pod manifest accepted, written to etcd
2. **Scheduler**: Pod bound to a node
3. **kubelet**: watches for Pods bound to its node
4. **kubelet**: calls containerd CRI `RunPodSandbox`
5. **containerd**: creates the pause container (network/IPC namespace holder)
6. **containerd**: calls the CNI plugin to configure the Pod network namespace
7. **kubelet**: calls containerd CRI `CreateContainer` for each container
8. **containerd**: pulls the image if not cached; prepares an overlay snapshot
9. **containerd**: calls `runc` with an OCI bundle (`config.json` + rootfs)
10. **runc**: reads `config.json` (namespaces, cgroups, mounts, capabilities)
11. **runc** executes:
    - `clone()` with namespace flags
    - Joins the cgroup hierarchy
    - Sets up mounts (overlay, proc, sys, devpts, volumes)
    - Drops capabilities, sets the seccomp profile
    - `execve()`s the container entrypoint
12. Container process runs as PID 1 in its namespace
13. **kubelet**: monitors via CRI `ContainerStatus` calls

## Chapter 11: Container Runtime Deep Dive

### Container Runtime Interface (CRI)

The Container Runtime Interface (CRI) is the gRPC API that Kubernetes uses to communicate with container runtimes. Any runtime implementing CRI can serve as a Kubernetes container runtime. This decoupling enables runtime choice without Kubernetes code changes.

| Runtime | Architecture | OCI Runtime | Best For | GPU Support |
| --- | --- | --- | --- | --- |
| containerd | Daemon + snapshotter + OCI executor | runc (default), kata-runtime | General purpose, production default | NVIDIA GPU Operator, CDI |
| CRI-O | Lightweight, K8s-specific daemon | runc, kata | Red Hat OpenShift, minimal footprint | Same as containerd via CDI |
| gVisor (runsc) | Intercepting kernel sandbox | runsc (user-space kernel) | Untrusted workloads, SaaS | Limited (no CUDA) |
| Kata Containers | VM-based container isolation | kata-runtime → QEMU/Firecracker | High-security, multi-tenant | Kata + GPU passthrough |
| Firecracker | MicroVM, sub-second boot | firecracker-containerd | Serverless (AWS Lambda) | Emerging support |
| Podman | Daemonless, rootless | runc, crun | Developer workstations, rootless | Via CDI |

### Kata Containers — VM-Level Isolation in Kubernetes

Kata Containers runs each container (or Pod) inside a lightweight virtual machine, providing hypervisor-level isolation while maintaining OCI/CRI compatibility. This is the standard approach for multi-tenant Kubernetes where workloads from different tenants must not share a kernel.

```yaml
# Enable Kata Containers via RuntimeClass:
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata-containers
handler: kata
---
# Use Kata in a Pod spec:
spec:
  runtimeClassName: kata-containers
  containers:
    - name: untrusted-workload
      image: customer-code:latest
```

Trade-offs vs. standard `runc`:

| Dimension | Kata Containers |
| --- | --- |
| Isolation | Hypervisor boundary (much stronger) |
| Startup | +200–500ms (VM boot vs. process fork) |
| Memory | +50–100MB per Pod (VM overhead) |
| Performance | ~5–10% CPU overhead vs. runc |

## Chapter 12: Kubernetes Leverage of Linux Primitives

Kubernetes is a high-level orchestration API built entirely on Linux primitives. This chapter provides the definitive mapping from Kubernetes abstractions to their Linux kernel implementation.

| Kubernetes Concept | Linux Primitive | Implementation Detail |
| --- | --- | --- |
| Pod isolation | PID + Net + Mnt + UTS + IPC namespaces | 6 namespaces per Pod sandbox (pause container holds net/ipc) |
| Pod IP address | Network namespace + veth pair + CNI | Each Pod gets a dedicated netns; CNI assigns IP via veth |
| CPU requests | CFS `cpu.weight` (cgroups v2) | Relative scheduling weight; prevents starvation |
| CPU limits | CFS bandwidth (`cpu.max`) | Throttles to N ms per period; source of latency spikes |
| Memory limits | cgroups `memory.max` | Hard limit; exceeding triggers OOM kill of the container process |
| Memory requests | cgroups `memory.high` + scheduler | Scheduler uses this for node placement; `memory.high` is a soft limit |
| Service ClusterIP | iptables DNAT / eBPF BPF map | Virtual IP implemented as a packet rewrite rule on every node |
| NetworkPolicy | iptables / eBPF / Calico Felix | Per-pod L3/L4 ACLs; eBPF enables L7 policies |
| Volume (emptyDir) | tmpfs mount / bind mount | tmpfs for memory-backed; node directory for disk-backed |
| Volume (PVC) | CSI mount + bind mount into netns | CSI driver mounts device/NFS; kubelet bind-mounts into Pod netns |
| ConfigMap/Secret | tmpfs + projected volume | Files are tmpfs-backed; Secrets never touch disk (in-memory) |
| Container image | OverlayFS layers | Lower dirs = image layers; upper dir = writable container layer |
| `runAsNonRoot` | `setuid()`/`setgid()` | `runc` sets UID/GID before `execve()`; kernel enforces |
| capabilities | Linux capabilities (`cap_set_proc`) | `runc` drops all caps then adds only specified ones |
| `seccompProfile` | seccomp BPF filter | BPF filter attached to the process; blocks specified syscalls |
| AppArmor | Linux Security Module (LSM) | Per-container AppArmor profile loaded from the node |
| QoS Guaranteed | cgroup `oom_score_adj = -997` | Protected from OOM kill; last evicted under node pressure |
| Node affinity | Scheduler + kubelet node labels | Scheduler uses topology info; no kernel primitive involved |
| GPU resources | cgroups devices + NVIDIA drivers | Device plugin exposes GPU via CDI; cgroup controls access |

## Chapter 13: Troubleshooting with Linux Tools

### Essential Diagnostic Command Reference

**Namespace and container inspection:**

```bash
# Get Pod PID on node:
crictl pods --name <pod-name>
crictl inspect <container-id> | jq '.status.pid'

# Enter Pod network namespace (diagnose connectivity):
nsenter -t <pid> -n -- ip addr
nsenter -t <pid> -n -- ip route
nsenter -t <pid> -n -- ss -tlnp
nsenter -t <pid> -n -- iptables-save

# Enter Pod mount namespace (inspect filesystem):
nsenter -t <pid> -m -- ls -la /
nsenter -t <pid> -m -- cat /proc/mounts

# Inspect cgroup limits for a Pod:
CGPATH=/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/kubepods-pod<uid>.slice
cat $CGPATH/memory.max
cat $CGPATH/cpu.max

# Check CPU throttling:
cat $CGPATH/cpu.stat | grep throttled
```

**eBPF-based observability:**

```bash
# Trace all exec() calls on the node (detect unexpected processes):
bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%s -> %s\n", comm, str(args->filename)); }'

# Trace TCP connections established by Pods:
bpftrace -e 'tracepoint:tcp:tcp_connect { printf("pid=%d comm=%s\n", pid, comm); }'

# CPU flamegraph using BCC perf tools:
profile -F 99 -p <pid> 30 > out.txt
flamegraph.pl out.txt > flamegraph.svg

# Pixie: zero-instrumentation observability for K8s
# Automatically instruments Go, Java, Python, Node via uprobes
px run px/service_stats -- --service=<name>
```

### Common Linux-Level Kubernetes Issues

| Issue | Symptom | Diagnosis & Fix |
| --- | --- | --- |
| Pod OOMKilled | Container exits with OOM kill | Check `memory.max` vs. usage: `kubectl top pod` + node event logs. Increase memory limit or reduce application memory usage. |
| CPU Throttling | Service latency without high CPU usage | Check `container_cpu_cfs_throttled_seconds_total` metric. Increase CPU limit or remove it; verify CPU requests match actual usage. |
| DNS resolution failures | Pods cannot resolve service names | `nsenter` into pod netns: `nslookup kubernetes.default`. Check CoreDNS pods, `ndots` setting, search domains. |
| iptables rule exhaustion | Service connectivity intermittent | Check iptables rule count: `iptables -L \| wc -l`. Consider IPVS mode or Cilium if >10,000 services. |
| OverlayFS disk full | Container cannot write files | Check ephemeral storage: `kubectl describe pod`, `df -h /var/lib/containerd`. Consider `emptyDir` with `sizeLimit`. |
| Zombie processes | PID namespace fills with defunct processes | Application not reaping children (the PID 1 problem). Add `tini` or `dumb-init` as PID 1 in the container. |

## Chapter 14: Hands-On Exercises

### Exercise 2.1 — Namespace Exploration

Deploy a test Pod and directly inspect its Linux namespace isolation:

```bash
kubectl run debug-pod --image=nginx:alpine --restart=Never
kubectl wait --for=condition=Ready pod/debug-pod

# Find Pod PID on node (SSH to node or use node debug):
kubectl debug node/NODE_NAME -it --image=ubuntu -- bash

# Use crictl to find pod PID:
POD_ID=$(crictl pods --name debug-pod -q | head -1)
POD_PID=$(crictl inspect $POD_ID | python3 -c 'import sys,json; d=json.load(sys.stdin); print(d["status"]["pid"])')

# List all namespaces of the Pod:
ls -la /proc/$POD_PID/ns/

# Compare host vs container PID namespaces:
ls -la /proc/1/ns/pid          # host init
ls -la /proc/$POD_PID/ns/pid   # pod -- different inode

# Inspect network namespace:
nsenter -t $POD_PID -n ip addr
nsenter -t $POD_PID -n ip route
nsenter -t $POD_PID -n ss -tlnp
```

### Exercise 2.2 — cgroups Resource Enforcement

Observe how Kubernetes CPU and memory limits translate to cgroup values:

```yaml
# Deploy Pod with resource limits (save as resource-demo.yaml and kubectl apply):
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
spec:
  containers:
    - name: app
      image: nginx:alpine
      resources:
        requests:
          cpu: 250m
          memory: 128Mi
        limits:
          cpu: 500m
          memory: 256Mi
```

```bash
# Find the cgroup path on the node:
POD_UID=$(kubectl get pod resource-demo -o jsonpath='{.metadata.uid}')
CGPATH=/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice

cat $CGPATH/kubepods-pod${POD_UID}.slice/memory.max
# Expected: 268435456 (256 * 1024 * 1024)

cat $CGPATH/kubepods-pod${POD_UID}.slice/cpu.max
# Expected: 50000 100000 (50ms quota per 100ms period = 500m CPU)
```

### Exercise 2.3 — eBPF Observability

Use eBPF tools to observe container behaviour:

```bash
# Install bpftrace on a Kubernetes node:
apt-get install -y bpftrace

# Observe all exec() syscalls (detect unexpected binaries running in pods):
bpftrace -e '
tracepoint:syscalls:sys_enter_execve {
  printf("%d %-20s %s\n", pid, comm, str(args->filename));
}'

# Observe all TCP connections established from pods:
bpftrace -e '
tracepoint:sock:inet_sock_set_state /args->newstate == 1/ {
  printf("CONNECT pid=%d comm=%s\n", pid, comm);
}'

# Generate a CPU flamegraph for a running pod
# (requires Linux perf + flamegraph.pl):
perf record -F 99 -p $POD_PID -g -- sleep 30
perf script | stackcollapse-perf.pl | flamegraph.pl > cpu.svg
```
