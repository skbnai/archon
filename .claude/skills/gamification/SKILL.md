# Gamification (reading streaks, section progress, quizzes)

## How it works

- Everything is client-side. `src/lib/progressStore.js` wraps
  `window.localStorage` under key `archon:progress:v1` — page visits, a
  daily streak, and quiz best-scores. Nothing is sent to a server; there is
  no backend and none should be added for this feature (single static
  GitHub Pages deploy target — see `governance/DOCUSAURUS_SETUP.md`).
- `src/clientModules/trackVisits.js` is a Docusaurus client-module
  (`onRouteDidUpdate`) that records a visit on every route change. It's
  registered in `docusaurus.config.js` under `clientModules`. It does NOT
  use React Router hooks — Root.js renders outside the Router, so page-visit
  recording lives here instead, not in Root.js.
- `src/theme/Root.js` only mounts the floating streak widget and listens for
  `PROGRESS_UPDATED_EVENT` (`src/lib/progressEvents.js`). Every write in
  `progressStore.js` dispatches that event so mounted components refresh
  live in the same session — don't poll, listen for the event.
- `src/data/progress-manifest.json` is generated — never hand-edit it. It's
  rebuilt by `scripts/build_progress_manifest.js`, which runs automatically
  via the `prestart`/`prebuild` npm hooks in `package.json`. Regenerate
  manually after adding a page: `node scripts/build_progress_manifest.js`.

## Embedding a progress bar on a hub page

Every domain/track hub (`docs/<domain>/index.md`) carries a
`SectionProgress` bar right before `## Scope`. Import goes right after
frontmatter:

```mdx
import SectionProgress from '@site/src/components/SectionProgress';

<SectionProgress domain="agentic-systems" />

## Scope
```

`domain` must match the docs folder name exactly (it's the manifest key). If
you register a brand-new domain in the taxonomy, add its display label to
`DOMAIN_LABELS` in `scripts/build_progress_manifest.js` in the same change —
otherwise the bar falls back to the raw folder name (a warning prints at
build time, it doesn't fail the build).

## Embedding a quiz

Use sparingly — one quiz per hub or capstone page, not per page. Questions
must be answerable from content already on that page (no outside knowledge
required, no ungrounded factual claims — see research-grounding).

```mdx
import Quiz from '@site/src/components/Quiz';

<Quiz
  id="agentic-systems-basics"
  title="Check your understanding"
  questions={[
    { question: "…", options: ["…", "…", "…"], answer: 1 },
  ]}
/>
```

- `id` must be globally unique repo-wide and stable — changing it resets
  readers' saved scores for that quiz. Kebab-case, prefixed with the domain
  (e.g. `agentic-systems-basics`).
- 3–5 questions; exactly one correct `answer` index per question (0-based,
  must be within the `options` array bounds).
- Voice follows page-styling: no hype, no trick questions, no joke options
  presented as if they were plausible technical answers.

## Keeping it in sync

- New domain/track registered (librarian agent) → add its label to
  `DOMAIN_LABELS` in `scripts/build_progress_manifest.js` → add the
  `SectionProgress` embed to its hub → regenerate the manifest.
- New page added to an existing domain → `_index.json` is regenerated by
  the graphify skill; re-run `build_progress_manifest.js` so the
  denominator picks it up (the npm `pre*` hooks do this automatically on
  the next `start`/`build`; run it manually if you need it inline sooner).
- Never hardcode a page count anywhere — always read it from the manifest.
- The `gamification-curator` agent owns auditing all of the above; run it
  after any docs/ restructuring, not just after adding pages.

## Accessibility & scope boundaries

- `SectionProgress` renders `role="progressbar"` with `aria-valuenow` /
  `aria-valuemin` / `aria-valuemax` — keep those when editing it.
- `Quiz` uses native `<fieldset>`/radio inputs — keep it keyboard-operable;
  no custom click-only widgets, no relying on color alone (the "✓ correct"
  marker is text, not just a color change).
- This skill is scoped to streaks, per-section progress, and quizzes only.
  Points/XP/levels/badges/leaderboards are explicitly out of scope for this
  site (no backend, single-reader local data, no way to compare across
  readers) — don't add them without a separate decision.
