# Archon Sidebar Maintenance

`sidebars.js` at the repo root is the reader's map of this wiki. It must
match `governance/SIDEBAR_GUIDE.md` (the structure rules) and
`governance/TAXONOMY.md` (the fixed domain list and order) exactly — treat
both as the live source of truth and **read them fresh every time this skill
runs**, not from memory. They govern this repo and can change independently
of this skill file.

## Before doing anything: read three files

1. `governance/SIDEBAR_GUIDE.md` — full structure rules.
2. `governance/TAXONOMY.md` — the 11 domains, their fixed order, and scope.
3. `sidebars.js` itself — current state. Don't assume you remember it; it
   changes every time a wave lands.

If the task involves restructuring a specific domain, also read every
`docs/<domain>/**/*.md` filename (not the content, just the file list) so
your proposal is grounded in what actually exists today, not a guess.

## The one technical gotcha that breaks builds

**Docusaurus strips the numeric ordering prefix from filenames when deriving
doc ids.** A file at `docs/platforms/05-ai-gateway-full-comparison.md` has
doc id `platforms/ai-gateway-full-comparison` — **not**
`platforms/05-ai-gateway-full-comparison`. The same stripping applies to
files under a `parts/` subfolder (`docs/platforms/parts/05-foo-part2.md` →
`platforms/parts/foo-part2`). The prefix exists purely to order files in the
filesystem; it is not part of the doc's identity.

Get this wrong and `npm run build` fails with:
```
Invalid sidebar file at "sidebars.js".
These sidebar document ids do not exist:
- platforms/05-ai-gateway-full-comparison
```
which is easy to misread as "the page doesn't exist" when actually the page
exists fine — only the id is wrong.

**Always verify a doc id by checking the real filename with its prefix
stripped**, and **always run `npm run build` after any sidebar edit** before
calling the work done. A clean build is the only real proof the ids resolve
— reading the JS back to yourself is not enough.

## Structure rules (condensed — SIDEBAR_GUIDE.md is authoritative)

1. **One top-level category per domain**, in this fixed order (from
   TAXONOMY.md): Strategy & Operating Model → Architecture → Agentic Systems
   → Protocols & Interoperability → Data & Knowledge → Platforms &
   Infrastructure → Trust: Security, Governance & RAI → Operations &
   Economics → Learning Paths → Career & Skills → Asset Library.
2. **Curate, don't autogenerate.** Every published category uses an explicit
   `items` array in deliberate reading order. `{type: 'autogenerated', ...}`
   is only acceptable as a temporary staging view under `migration/` during
   an active wave — never in a merged, reader-facing category.
3. **Every category anchors to its hub**: `link: { type: "doc", id:
   "<domain>/index" }`, so clicking the category label opens the curated hub
   page rather than just expanding an empty folder.
4. **Reading order inside a category**: hub first, then foundational
   concepts, then guides/reference-architectures, then reference/checklist
   material last. A multi-part series (Part 1/2/3..., Vol 1/2/3...) stays
   contiguous and in numeric order — never split across two sub-categories or
   reordered by topic.
5. **Nesting depth ≤ 2** inside a domain (domain → sub-category → doc). If
   you're reaching for a third level, that's the signal the domain needs its
   own sub-hub page instead of deeper sidebar nesting.
6. **Collapsed by default**: `collapsible: true`. Don't hardcode
   `collapsed: false` per-category — Docusaurus expands the active path
   automatically.
7. **Labels**: exact domain display name from TAXONOMY.md, Title Case, no
   emoji, no unexplained abbreviations (spell out "RAI" once as "Responsible
   AI" or similar, acronym is fine after that in sub-items).
8. **Every new page enters the sidebar in the same PR that adds the page.**
   A page in `docs/` with no sidebar entry is an orphan. This is the rule
   most often missed by a migration/bundle PR that adds pages without
   touching `sidebars.js` — check for this specifically after any migration
   wave lands.

### Special-section exceptions

- **Learning Paths** and **Career & Skills**: flat lists, no sub-categories
  — these are already-curated journeys; nesting adds friction, not clarity.
- **Asset Library**: sub-categorize by engagement phase (Discovery, Design,
  Delivery, Operate) — never by file type (templates vs. checklists vs.
  transcripts).
- **ADR library** (`docs/architecture/adr/`): its own sub-category under
  Architecture, sorted by ADR number, newest last.

### Scoped maintenance

When asked to fix, add to, or reorganize the sidebar, touch only the entries
actually in scope (the new pages, or the category being restructured). Don't
re-verify or rewrite already-correct sections just because the file is open
— **Protocols & Interoperability and Data & Knowledge are the two
domains currently structured correctly** (clean sub-categories, hub links,
sane depth); use them as your reference examples of "what good looks like"
when proposing a fix elsewhere, don't modify them unless something in them
is actually broken.

## Auditing the sidebar

Walk `sidebars.js` domain by domain and check, for each category:

- Does `link.id` point at a real `<domain>/index` doc?
- Is `items` an explicit array (not autogenerated)?
- Is nesting ≤ 2 levels?
- Any single flat `items` array with more than ~15-20 entries and no
  sub-category grouping? That's a strong overload signal (see Strategy &
  Agentic Systems below — both currently fail this).
- Any multi-part series split across sub-categories or out of numeric order?

Then cross-reference against the filesystem:

```bash
# Every doc/*.md file, prefix stripped, domain-relative — what SHOULD be
# referenceable from the sidebar:
find docs/<domain> -name "*.md" ! -name "index.md" \
  | sed -E 's#^docs/##; s#/[0-9]+-#/#; s#\.md$##'

# Orphans: pages that exist on disk but appear nowhere in sidebars.js
# (grep each id above against sidebars.js and report misses)

# Broken entries: sidebar ids referencing files that don't exist
# (the npm run build check below is the authoritative version of this)
```

`npm run build` is the ground truth for "every sidebar id resolves" — treat
a clean build as required before reporting an audit as complete, not
optional polish.

## Restructuring an overloaded domain

Two domains are currently known to be overloaded (52+ pages in one flat
list) and are the most likely restructuring targets:

**Strategy & Operating Model** (`docs/strategy/`) — currently one giant flat
`items` array with no sub-categories at all. A reasonable starting split,
**to verify against the actual current file list before finalizing** (this
is a starting proposal, not a fixed answer — file counts and content shift
as waves land):
- Vision & Foundations
- Enterprise Strategy Handbook
- Research Series
- Value / Economics
- Transformation
- Market & Landscape

**Agentic Systems** (`docs/agentic-systems/`) — already has sub-categories
(`Core Agent Concepts`, `Agentic UI & Applications`, `Coding Tools &
Assistants`, `Multimodal AI`, `Orchestration & Workflow Engines`), but
**"Core Agent Concepts" alone (mapping to `docs/agentic-systems/core/`) is
itself a 50+ item flat list** — the overload is one level deeper than it
first looks. Don't just re-propose "split into Core Agent Concepts and
Coding Tools" (Coding Tools is already split out); instead read the actual
file list under `docs/agentic-systems/core/` and group by sub-theme (e.g.
agent-skill lifecycle, harness engineering, config/asset management,
multi-tenant platform ops) the same way Protocols groups by sub-theme today.

When you propose a restructuring, always:
1. Read the real current file list for that domain first — the candidate
   groupings above are hypotheses, not answers.
2. Keep series contiguous and numeric.
3. Preserve every existing doc id exactly (a restructuring reorders/regroups
   entries, it doesn't change what ids exist elsewhere in the app).
4. Output the complete replacement `items` array for that category as a
   ready-to-paste JS fragment, plus a short rationale for the grouping.

## Adding a new page

1. Find the file's real doc id (path relative to `docs/`, numeric prefix
   stripped, no `.md`).
2. Decide which existing sub-category it belongs to by topic — if none
   fits, that's a legitimate reason to propose a new sub-category, following
   the reading-order rule (foundational → practitioner → expert) for where
   it lands.
3. If it's part of a series, place it contiguously with its siblings in
   numeric order.
4. Edit `sidebars.js` directly — don't regenerate the whole category unless
   asked to restructure.

## After any sidebar change

1. Regenerate the machine-readable section index so it doesn't drift from
   the human-facing nav:
   ```bash
   python3 .claude/skills/graphify/scripts/build_section_indexes.py
   ```
2. Run a clean build to prove every id resolves:
   ```bash
   rm -rf build .docusaurus && npm run build
   ```
   A pre-existing "broken anchors" warning (in-page `#heading` links, not
   sidebar doc ids) is a separate, non-fatal issue — don't confuse it with a
   sidebar failure. A sidebar id problem shows up as `[ERROR] ... Invalid
   sidebar file` and a non-zero exit code; anchors are `[WARNING]` only.

## Output format

When proposing a fix or restructuring, give:
1. **Rationale** — what's wrong (cite the specific SIDEBAR_GUIDE.md rule)
   and why the proposed grouping fixes it.
2. **The exact JS fragment** — ready to paste into `sidebars.js`, matching
   existing indentation/quote style (double quotes, 2-space indent, trailing
   commas as seen elsewhere in the file).
